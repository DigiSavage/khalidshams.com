01 · Choose the design

The task chooses the pattern. Governance sets its reach.

I keep architecture and authority separate. A more capable model does not earn more permission, and more agents do not automatically complete more work.

These choices produce a review proposal. They cannot authorize a real deployment. Start with read-only access when the consequences are unknown.

Enforce these rules at retrieval and tool execution. A prompt, skill, MCP connection or approval screen cannot replace server-side authorization. A delegated agent receives the intersection of its own scope and the caller's scope, never broader inherited powers.

Leave this gate with

Identity and data-flow diagrams, tool schemas, input validation, reviewer roles, expiration rules, idempotency, a retry policy and a tested stop path.

A · Anchor · Gate 04

Make evidence traceable all the way back.

{{INGESTION}}

{{GROUNDING}}

Evidence card · synthetic example

{{SOURCES}}

Separate the source of truth, the search index, the current context and stored conversation state. Each has its own access and deletion rules. Re-check permission on later turns; do not let a cache or memory reintroduce revoked material.

Leave this gate with

A source register, ingestion and deletion pipeline, permission propagation tests, citation format, freshness rule and an explicit insufficient-evidence outcome.

M · Measure · Gates 06, 07

Prove the outcome, including the failures.

{{QUALITY}}

Compare the full system with its baseline on the same held-out tasks. Repeat variable model trials. Check the final business state in code, use domain reviewers for judgment, and calibrate model graders against those reviewers. Report denominators and failures by slice.

{{ACCEPTANCE}}

Total cost per accepted outcome = model + extraction + search + infrastructure + retries + human review, divided by accepted outcomes. If none succeed, report no successful outcome, not a zero cost.

Leave this gate with

A versioned test set, agreed quality and latency thresholds, a risk review, unit economics and release criteria. No universal confidence score or benchmark can approve this system for your estate.

S · Sustain · Gate 08

Release a version you can observe and withdraw.

{{OPERATION}}

Progress from offline tests to shadow operation, then a limited pilot and a staged release when agreed gates pass. Shadow runs do not execute business writes. Pin the prompt, model deployment, retrieval configuration, policy and tool schema together.

Leave this gate with

An on-call owner, incident thresholds, a review queue with an escalation time, versioned release evidence, rollback instructions and a tested kill switch. Stopping an agent does not undo completed external actions; reconcile them separately.

04 · Map it to a platform

Keep the control plane. Choose the model deliberately.

This is a reference architecture I would adapt to the client's estate. The model is a replaceable component inside a governed application, with a documented processing boundary.

Pin an approved model deployment and API version. Confirm region, networking, residency, retention, quotas and lifecycle for that specific deployment.

Confirm the exact hosting version, region, terms and lifecycle; do not infer data residency from the Azure portal. Configure applicable inference-time content safety instead of assuming deployment-time filtering. Availability · Data processing.

What changes when I introduce Anthropic models?

I preserve application authorization, evidence provenance, tool contracts and approval records. I replace the model adapter, check message and tool-use semantics, rerun the evaluation suite and verify the selected endpoint's data-processing terms. Direct Anthropic API access is a separate procurement and data-flow decision from either Foundry hosting option. A model fallback also needs approval for its data boundary and a passed evaluation; it must not silently reroute sensitive content.

A specialist architecture needs independent evaluation of delegation and result aggregation. Specialists get bounded work orders, limited context and a shared run identifier. Only the authorized execution service can commit a business change. The coordinator cannot manufacture permission by asking a different specialist.

05 · Observe and improve

Every improvement is a versioned change.

I ask which part failed before deciding what to train. A thumbs-up, a longer prompt and a model upgrade are different interventions. None bypasses release evaluation.

Diagnose first

Find the component that failed.

{{IMPROVEMENT}}

Update the source or retrieval

Repair approved content, permissions or indexing. Re-evaluate retrieval and answers. This updates evidence, not language-model weights.

  1. Capture a failureMinimized trace, outcome and source versions.
  2. Review and labelDomain owner adjudicates; remove sensitive content.
  3. Change one componentSource, retriever, prompt, tool, policy or model.
  4. Evaluate on held-out casesCompare with baseline; test neighboring failure modes.
  5. Approve and releaseShadow, pilot, monitor; withdraw on agreed triggers.

Monitor the task, the boundary and the service.

Business outcome

Accepted results, correction and rework, unresolved cases, reviewer workload and time to completion.

Governance

Denied calls, authorization changes, evidence failures, approval age, unexpected tool use and deletion lag.

Operations

p95 latency, timeouts, retries, tokens, cost per accepted result, source age and version-level regressions.

Log correlation IDs, versions, source identifiers, policy decisions, redacted tool arguments and verified results. Capture sensitive payloads only under an explicit access and retention policy. Traces show observed behavior; they do not reveal a model's complete internal reasoning or prove the answer correct.

How I build agentic AI

Eight gates between a demo and a system.

Most agent demos work. Most agent systems don't. The difference isn't the model. It's a short list of questions that have to be answered in writing, in order, before the next step is allowed to happen. I run every agentic build through the same eight gates. Each gate is one question, the evidence that answers it, and the name of the person who signs.

In order

Gates 1 to 4 are answered before a line of orchestration code exists. They take about a week and they decide most of the architecture.

In writing

Every gate produces one page. Question, answer, evidence, owner, date. If it won't fit on a page, the thinking isn't done.

With a signature

A gate isn't passed because the architect says so. The person accountable for that gate signs it, and a gate can be reopened when something changes.

Gate 01 · Decision

What decision does this system make, and who owns it when it's wrong?

Why it matters

Vague scope is how an agent does the wrong thing confidently. "It helps users with X" is not a decision. A system that decides which invoice to pay is a different build from one that drafts the email asking about it, and nobody can design the controls until that line is drawn. The owner question is the one that stalls projects: if the answer is a committee, the project isn't ready.

What I produce

  • A one-page scope statement: the decisions in scope, the decisions explicitly out, and the cost of a wrong answer in dollars or harm.
  • One named accountable owner for the outcome, not for the build.
  • The three questions, answered in writing: who is accountable, what is it allowed to see, what does a run cost at ten times the volume.

Not through this gate if

  • The scope is a list of use cases rather than decisions.
  • Nobody can say what a wrong answer costs.
  • Accountability is "the AI team."

From the work

In the clinical platform I architected, the system never decides a diagnosis. It decides which document goes to which human queue, and how urgently. Writing that sentence down shaped everything that followed.

Gate 02 · Boundaries

What does each agent own, where does control pass, and where does a human sit?

Why it matters

Handoffs are where failures hide. One "do everything" agent can't be tested, priced, or explained. A pipeline of narrow specialists with a planner on top can be swapped piece by piece. And a human in the loop is only a control if the loop was designed: if the review screen is bad, the human stops reviewing and starts approving.

What I produce

  • An agent map: one box per agent with its inputs, outputs, and the condition under which it hands off.
  • Human decision points placed by consequence, not by convenience, each with a designed review surface.
  • The queue: priority by consequence, a service level per item type, one owner per item, reason codes on every rejection.

Not through this gate if

  • There is one agent and a very long prompt.
  • "Human in the loop" is an Approve button nobody designed.
  • Handoffs happen inside the model's reasoning rather than in the architecture.

From the work

On the system I delivered on Anthropic's Claude platform, the planner decomposes the task and specialists retrieve, analyse, and act, each with a bounded scope and an explicit handoff. The planner is where the care goes.

Gate 03 · Permissions

What is the agent allowed to see and do, per user, enforced by the platform?

Why it matters

The most common enterprise AI failure I've seen isn't a hallucination. It's a service principal with broad access wired in during the pilot, and an assistant that cheerfully returns data the user was never cleared for. Policy in the prompt is a suggestion. Policy in the platform is a control.

What I produce

  • An identity model where the agent acts as the user and inherits the user's permissions, never exceeding them.
  • Per-tool permission scopes; the service identity does only what no user could.
  • Entra ID, RBAC, and just-in-time elevation for anything privileged, with an access log that answers "who saw what, on whose behalf."

Not through this gate if

  • The service principal has Contributor on the subscription.
  • "Don't reveal confidential data" appears in the system prompt as the control.
  • Nobody can list what the agent can reach.

From the work

Governance isn't the brake. On the security and data strategy work I contributed to, controls landed before workloads, so the AI features inherited governance instead of fighting it.

Gate 04 · Grounding

Where does every fact come from, and is that source governed?

Why it matters

If the data underneath isn't governed, the agent is fluent and wrong. Retrieval systems rarely fail loudly; they drift. Stale indexes, permissions that changed after indexing, chunks that lost their context, citations to documents that no longer exist. And the moment an agent keeps its own copy of a fact, you have a second source of truth that nobody governs.

What I produce

  • A source inventory with a named owner for every source, usually a governed gold layer rather than a folder someone made for the pilot.
  • Provenance on every answer: retrieval attaches where it came from and whether it's current.
  • The retrieval-versus-memory rule, written down: facts about the world are retrieved, never remembered. Index refresh tied to source change events. Permission checks at query time, not index time.

Not through this gate if

  • The index was built once from a demo folder.
  • Answers have no citation, or citations that 404.
  • The team says the agent "remembers" things.

From the work

Moving an estate onto Microsoft Fabric with real medallion layering changed the question from "where is the data" to "who owns this layer." That ownership is what made grounding an agent on it safe.

Gate 05 · Actions

Is every write typed, validated, idempotent, and reversible?

Why it matters

An agent will retry. That isn't a bug, it's how they work. If a tool sends an email, creates a ticket, or moves money, and the first call succeeded, you now have two. A tool call is an API call and deserves the same discipline as any other integration, and in most prototypes it gets none.

What I produce

  • A contract per tool: typed input validated before execution, typed output, a description written for the model, a version, a permission scope, and a defined failure path.
  • Idempotency on every write: a request id the receiving system dedupes on, or a write that sets state rather than adds to it.
  • Reversibility where possible: drafts before sends, holds before transfers, proposals before merges. A blast-radius table listing what each tool can break.

Not through this gate if

  • Tools take an untyped dictionary and return whatever comes back.
  • Nobody can answer "what happens if this is called twice."
  • Model output goes straight into a downstream step without a schema check.

From the work

In the clinical system, name matching proposes and never merges. A human confirms that two records are one person, and that decision is logged with who made it. The source document stays immutable, forever.

Gate 06 · Evaluation

Can you show me the harness, and what number moves when quality moves?

Why it matters

Every change to an agentic system, whether a prompt, a tool, a model version, or a retrieval tweak, has an unknown blast radius. Without a regression suite you aren't iterating. You're gambling and calling it iteration. If the answer to "show me the harness" is a pause, you're looking at a prototype wearing production clothes.

What I produce

  • A fixed case set that includes the ugly inputs, not just the happy path.
  • A written catalogue of known failure modes, grown from every rejection in the review queue.
  • Groundedness and citation checks, so "confident" and "correct" don't get confused. One quality number and one cost number on the same dashboard, and a rule that no prompt or model change ships if either moves the wrong way.

Not through this gate if

  • Quality is "it looked good in the demo."
  • An evaluation exists but isn't run before changes.
  • There is no number that moves when quality moves.

From the work

The Claude platform build shipped with an evaluation harness and a written failure-mode catalogue as deliverables, not afterthoughts. That's what let production hardening happen in weeks instead of quarters.

Gate 07 · Economics

What does a run cost at ten times the volume?

Why it matters

A license costs the same whether people use it or not. An agent costs more the better it works, sometimes faster than linearly, because successful agents get asked harder questions and take more steps to answer them. Cost per run is an architecture decision, not a finance surprise.

What I produce

  • A token budget per run, enforced, with a graceful stop rather than a runaway loop.
  • Model routing: small, fast models for classification, extraction, and formatting; the frontier model only for steps that need judgment.
  • Caching where inputs are stable. Hard ceilings on tool calls, retries, and recursion depth. A cost line next to the quality line.

Not through this gate if

  • One model does everything.
  • Nobody can quote the most expensive run last week.
  • Finance will find out from the invoice.

From the work

On the platform I run alone on AWS, the cost alarm is set lower than I think I need. It has paid for itself three times. The same rule scales to an enterprise estate.

Gate 08 · Operations

Can you stop it, explain it, and change it safely?

Why it matters

Agents fail in ways that are fast, repetitive, and confident. By the time a human notices, the agent has done the wrong thing forty times. Logs tell you what it did; only a trace tells you why. And a model version change is a production deploy, whether or not the team treats it as one.

What I produce

  • An off switch someone can flip in under a minute, a read-only mode, and circuit breakers per tool.
  • A trace per run: the plan, each retrieval and what it ignored, each tool call, each rejected alternative, and the cost of every step.
  • Prompts as versioned configuration gated by the harness. Model versions behind feature flags, rolled to a slice first. Append-only audit. Pilot exit criteria with a date, written before the architecture.

Not through this gate if

  • Rollback is the only way to stop it.
  • There are logs but no traces.
  • The prompt was last edited in a console on a Friday afternoon.

From the work

Every pilot I scope now has its exit criteria in the first document: the numbers that trigger a production build, the numbers that trigger shutting it down, and a date. Both outcomes are wins. The only losing outcome is drifting into permanence.

One page per gate. This is the page.

Every gate ends in the same short record. It's deliberately plain so that it gets written, and so an auditor, a new engineer, or a future version of the team can read it in a minute.

GATE          03 · Permissions
QUESTION      What is the agent allowed to see and do, per user, enforced by the platform?
ANSWER        The agent runs as the signed-in user via on-behalf-of flow. It reaches the
              gold layer of the claims lakehouse and the ticketing API, nothing else.
              The service identity can only write traces and read configuration.
EVIDENCE      Identity diagram v3 · RBAC assignments export · access log sample from a
              test user with restricted scope returning a correct denial
OPEN ITEMS    PIM activation for the two privileged tools (owner: platform team, due 14 Nov)
OWNER         Head of Security Engineering
SIGNED        12 Nov 2026
REVISIT       When a tool is added, when a data source is added, or at 90 days

Why gates and not a checklist

Order is the whole method.

A checklist lets you do the exciting part first and tick the boundaries later. By then the exceptions are already in production and every control is a negotiation with something people depend on. Gates force the sequence: decide, bound, permit, ground, and only then build. It looks slower on the plan. It is the only version that stays fast. The writing is where each gate gets argued about in public, twice a week.
